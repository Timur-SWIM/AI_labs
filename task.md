## 3. Вкладка №1 — «Один нейрон» (5–12 мин семинара)

### Математика

`y_hat = w*x + b`, `L = (y - y_hat)^2` (на экране ясно указать, что здесь квадрат ошибки **без множителя 1/2**).

Исходно `x=2`, `y_target=7`, `w=1`, `b=0`. Контролы для `w` и `b`; мгновенное обновление `y_hat`, ошибки и линии/точки на графике.

### Сценарий 1: один пример

Студент вручную изменяет `w`, `b`, добиваясь `y_hat=7`. Показать, что подходящих пар параметров **бесконечно много**.

### Сценарий 2: два примера

Добавить `x=3`, `target=10`, дать переключатель «учитывать оба примера». Отображать **суммарную/среднюю** ошибку по двум примерам. Единственное решение для двух линейно независимых условий: `w=3`, `b=1`.

Дополнительно разрешить визуализацию прямой `y_hat(x)` относительно двух истинных точек; при одном примере показать неединственность ответа.

Вопрос студентам: «Что модель подбирает и почему одного обучающего примера недостаточно для однозначного нахождения двух параметров?»

## 4. Вкладка №2 — «Градиентный спуск» (12–20 мин)

### Математика и поведение

Использовать `L(w)=(w-2)^2`, `dL/dw=2(w-2)`, `w_next=w-lr*dL/dw`. Начальный вес `w=-1`, демонстрационное `lr=0.2`.

Реализовать:

- график **реальной** параболы и положение текущей точки;
- траектория шагов с номерами; таблица `step, w, gradient, lr, loss`;
- слайдер learning rate (например `0.01..1.5`);
- кнопки «Один шаг», «10 шагов», «Сброс»;
- историю Loss от номера шага;
- предупреждение при расходимости и NaN/Inf; точку не зажимать искусственно в диапазоне и не искажать математический ход оптимизации (допускается адаптивный масштаб осей и ограничение числа шагов);
- отдельные пояснения для малой скорости, устойчивой скорости, `lr=1` и `lr>1`.

Гарантированная точная проверка: при `lr=0.5` для данной функции первый шаг из `w=-1` приводит в `w=2` (минимум). При `lr=1` наблюдаются колебания между `-1` и `5`, не убывание Loss.

Вопрос: «Почему backpropagation — это не оптимизатор, а алгоритм вычисления градиентов?»

## 5. Вкладка №3 — «Живая MLP: преобразование координат» (20–45 мин)

Это центральная часть приложения. **Не сводить к вызову полного `run_all.py` с показом сохранённых PNG.**

### 5.1 Данные и входы

Визуализировать исходные точки в координатной плоскости, вход `rho, phi`, истинные `x,y`. Чётко показать, что формулы задают teacher labels, а сама сеть использует только обучающие примеры.

Разделить train/validation/control. Для демонстрации использовать исходное 60/20/20, seed 42. Не использовать control для выбора гиперпараметров или early stopping. Не допустить утечки нормализации: статистики вычислять **только на train**.

### 5.2 Управление сетью

Контролы:

- архитектура: пресеты `2-4-4-2`, `2-7-3-2`, `2-10-6-2` и безопасный ручной ввод скрытых слоёв;
- оптимизатор: `Adam`, `SGD (full-batch)`;
- скорость обучения (логарифмический диапазон, безопасные значения и отдельный режим эксперимента с чрезмерным шагом);
- число эпох, seed, начальная амплитуда весов `init_scale`, tolerance;
- optional «останавливать при 80% GF»;
- опции «обучение порциями» и «показывать состояние каждые N эпох».

### 5.3 ОБЯЗАТЕЛЬНО: настоящее пошаговое обучение

Текущий `MLPRegressor.fit()` вычисляет много эпох внутри одного блокирующего вызова, поэтому **реализуй корректный training step / train_n_epochs API**, а не имитируй обновление UI поверх заранее рассчитанной истории.

Например, аккуратно выделить объект состояния оптимизатора (`Adam`: моменты и счётчик шагов) с методами `step()` / `train_epochs(n)` так, чтобы:

- каждый шаг действительно менял веса;
- `Pause` сохранял состояние весов, biases, Adam moments, номер эпохи;
- `Resume` продолжал **тот же** эксперимент, не сбрасывая Adam;
- `Reset` создавал новую модель с указанным seed;
- история train/val loss, GF и контрольных предсказаний отражала реальные текущие веса;
- Streamlit rerun/сессионное состояние не смешивало эксперименты двух пользователей;
- вычисления выполнялись малыми batch-порциями между обновлениями экрана, **без фейковой анимации и без блокирующего бесконечного цикла**.

Постарайся сохранить совместимость `fit()` с существующим `run_all.py`; проверь численный паритет старого и нового обучения при фиксированном seed/параметрах. Если для интерактивного режима нужен отдельный движок, он должен использовать ту же математику и проходить тест сопоставления с `MLPRegressor`.

### 5.4 Одновременные визуализации

Не меньше следующих четырёх:

1. **Loss vs Epoch** — train и validation на одном графике; текущая эпоха выделена.
2. **Геометрия вектора** — правильный 00вектор `(x,y)` и предсказанный `(x_hat,y_hat)` из одного начала, отрезок ошибки между концами; интерактивный выбор тестового примера.
3. **True vs Predicted** — точки/линии x и y или диаграмма parity plot с диагональю `y_pred=y_true`.
4. **Матрицы весов** — heatmap текущих матриц `W` по слоям, показывающий изменение по ходу обучения (обязательно фиксировать масштабы цветов либо явно сообщать, что они изменились).

Плюс компактный блок KPI:

- эпоха, число параметров;
- `MSE_train`, `MSE_val`, `MSE_control` (control **только по специальной кнопке финальной оценки**, а не на каждом шаге/при подборе);
- GF/BF при указанном tolerance;
- текущие координатные ошибки `|dx|`, `|dy|`;
- статус обучения.

Не подменяй значения моделью из сохранённых результатов. Если контрольная оценка вызвана, пометь её как **итоговую**, и предупреди о нежелательности многократного использования для выбора параметров.


Внутри контейнера Streamlit слушает `0.0.0.0:8501`; снаружи порт привязан к loopback **Docker-хоста**. Это безопасный default, хотя наличие других сервисов/правил системы всё равно требует проверки.

### Важный сценарий: Docker на Ubuntu VM, браузер на физическом хосте

В README обязательно разъяснить отличие **localhost контейнера**, **localhost VM** и **localhost физического хоста**. При `127.0.0.1:8501:8501` внутри VM физический хост не сможет открыть `http://127.0.0.1:8501` напрямую — это его собственный loopback.

Предусмотреть минимум два документированных способа:

**Способ A (предпочтительный, безопасный): SSH-туннель от физического хоста к Ubuntu VM**

1. В Ubuntu VM включить SSH при необходимости (`openssh-server`), проверить SSH-доступ к VM.
2. `docker compose up -d --build` в VM (привязка docker-порта к 127.0.0.1 внутри VM).
3. На физическом хосте:

```bash
ssh -N -L 8501:127.0.0.1:8501 USER@VM_IP
```

4. На физическом хосте открыть `http://127.0.0.1:8501`.
5. На Windows привести эквивалентную команду в PowerShell (встроенный `ssh`), а при занятости порта — альтернативу `18501:127.0.0.1:8501`.

Примечание: если VM за NAT, понадобится настроить сеть/проброс SSH-порта гипервизора; пользователь должен знать адрес/порт SSH VM. Не считать, что все VM доступны по IP по умолчанию.

**Способ B (явный, менее приватный): доступ напрямую по IP VM**

Отдельным профилем/override-файлом, **не включённым по умолчанию**, опубликовать контейнерный порт на интерфейс VM (`0.0.0.0:8501:8501` или конкретный IP VM). Документировать:

- доступ из браузера физического хоста по `http://VM_IP:8501`;
- необходимость bridged/host-only сети или NAT port forwarding;
- риск видимости сервиса другим устройствам LAN;
- рекомендации к firewall Ubuntu, ограничению адресов, запрету проброса в интернет;
- вернуть закрытый localhost-only режим после семинара.

**Никаких инструкций по открытию порта на домашнем сервере преподавателя**. Все инструкции относятся только к локальному компьютеру или собственной VM студента.

Дай команды:

```bash
docker compose build
docker compose up -d
docker compose ps
docker compose logs -f
docker compose down
```

И healthcheck/тест в README с `curl` к `/ _stcore/health` без пробела (реальный путь Streamlit `/_stcore/health`; проверить версию).

## 11. Архитектура, безопасность и устойчивость

- Выделить математическую модель/обучение из UI; `app.py` не должен содержать 500 строк вычислительного кода.
- Переиспользовать общую математику без циклических импортов.
- Тестировать и явно обрабатывать неверные настройки: 0 нейронов, отрицательные эпохи, `lr<=0`, NaN, большие архитектуры, перегрузку CPU.
- Не выполнять произвольный Python из текстовых полей, `eval`, shell, загрузку `.pkl` из непроверенных файлов.
- Не открывать произвольные пути сервера через веб-интерфейс.
- У разных браузерных сессий разные модели и результаты. Не хранить изменяемую модель в глобальном `st.cache_resource`, доступном всем пользователям.
- Никаких API ключей, аккаунтов, cloud inference, внешних вызовов, обязательной регистрации и сетевой телеметрии.
- Ограничивать ресурсы экспериментальных запусков и корректно прекращать чрезмерно долгие вычисления.
- Во время остановки/возобновления обучения не терять весовые коэффициенты и внутреннее состояние Adam.
- Разработать так, чтобы повторное выполнение с одинаковыми данными, seed и конфигурацией давало одинаковые результаты (в пределах численной погрешности).
- Не использовать «реальное время» как обещание миллисекундной графической анимации; достаточно постепенных настоящих обновлений по порциям эпох.

## 12. Тесты и проверки (обязательно выполнить)

### Unit

- `y_hat=wx+b`, корректная ошибка для одного/двух примеров;

- аналитические/численные градиенты MLP согласованы (finite differences);
- `Pause -> Resume` даёт эквивалент продолжению без паузы (те же веса и моменты Adam);
- `reset with seed` воспроизводим;
- train-нормализация не зависит от test/control;
- MSE/GF/BF корректно вычисляются;
- независимые учебные сессии не разделяют изменяемую модель.

### Integration / UI

- тестовые сценарии A/B/C действительно дают заявленные наблюдения (проверить на фиксированных seed), а не поддельные демонстрационные кривые;
- запуск с `127.0.0.1:8501` и `GET /_stcore/health` успешен.

### Docker

- `docker compose config -q`;
- `docker compose build`;
- `docker compose up -d`;
- healthcheck healthy;
- `curl -f http://127.0.0.1:8501/_stcore/health`;

- после остановки порт свободен;
- при возможности отдельно проверить `linux/amd64` и `linux/arm64`, но если архитектура не проверялась — явно пометить.
